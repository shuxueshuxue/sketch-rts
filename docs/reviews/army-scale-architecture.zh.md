# 5000 单位模拟与寻路基准

本报告记录共享模拟的无画面基线与寻路优化。下列微基准不代表完整对局帧率，也不包含战略 AI。

## 测试边界

运行 `node --import tsx scripts/army-scale-probe.ts --units 5000 --ticks 200 --out <report.json>`。

每个场景初始 5000 个真实单位，使用正常生命值、碰撞、地形寻路、战术自动施法和伤亡；模拟 200 个逻辑帧，即游戏内 10 秒。三种场景为 5000 人绕林墙行军、2500 对 2500 混合兵种交战、五条战线交战。阵亡者不会补充，所以战斗后存活数量少于 5000。行军场景使用不同目的地，专门暴露大批请求对寻路缓存的压力。

不包括战略 AI、浏览器绘制、联网、六主动道具、多舰种和动态工程。普通战斗包含步兵、枪兵、弓手、骑士和牧师。报告的快照与编码费用单独测量，未加入逻辑帧时间。状态摘要每 20 帧及结束时计算，保留完整浮点值和数组顺序，其耗时也不计入逻辑帧。

基准在沙盒 Node v24.19.0 / AMD EPYC 9V74 环境执行，不代表用户电脑或线上 Node 20 的帧率。旧版本在独立工作树单独重跑；新版本连续重复两次。RSS 是同一进程在各场景结束时的总驻留内存，不能直接当作某场景独占或精确缓存占用。

## 瓶颈与本次修改

1. 目的地局部流场超过 2048 个后，旧实现会清空所有缓存。5000 个不同目的地导致重复建场。改为有界 8192 项 LRU，淘汰单个旧目标；每个路由层的局部场 typed arrays 上限约 56 MiB（不含其他数据与对象开销）。动态建筑更新仍按原逻辑使受影响的区域失效。
2. 对于同一连通区域内的开放目标格，直接回答可达性，无须为了读取一个目标种子先生成整块流场。
3. 自动冲锋只有找到范围内的合格目标后，才收集其他骑兵的冲锋目标。此前大量尚未接敌的骑兵也反复扫描全军。

优化不修改伤害、移动速度、寻路选择或随机性。用原版和新版在同一输入下的中间/结束状态摘要比对，外加地形、海军、冲锋、模拟与回放测试验证。

首次初始化仍有明显尖峰；大规模对局需要预热/分批构建导航，不能只报告稳态均值。缓存扩容是在内存预算内换取少算，并非无限增长方案。更大场景还应减少独立目标场数量，让军团共享路线并在局部处理队形。

## 技术路线与后续工作

- 继续用 TS 承载规则、剧情、UI 和调试工具。TS 类型会在编译时消除，实际运行性能由 JS 实现和执行引擎决定。
- 可评估把模拟移入专用 Web Worker，与主线程绘制分离；这可改善响应性，但不会自动缩短模拟耗时。服务端按对局分配线程也不同于单场对局并行。
- 战略 AI、路径请求按只读状态快照组成批量任务，交给持久 Worker 池。结果携带逻辑帧/地图版本/请求编号，在固定阶段按稳定顺序提交；不能让返回先后或机器快慢改变游戏行为。
- 逐步把热点的坐标、生命值、空间索引等转换为紧凑数组，减少临时对象、全军扫描及跨线程复制。客户端只传递渲染必需的紧凑状态，不每帧复制整个 GameSnapshot。
- 浏览器可用 Web Workers，Node 可用 Worker Threads；SharedArrayBuffer 方案需部署跨源隔离并处理同步，不是 Promise.all 就能获得多核。
- 保留现有手绘 sprite 美术，评估 WebGL2 图集批处理/实例绘制，减少大量 Canvas 调用。画风与绘制后端可以分开。
- 若测得某个计算内核仍占主要预算，再试 Rust/C++→WASM，按批次传入数组，比较端到端收益和状态一致性。WASM 不是自动并行，调用与数据搬运也有成本。
- 目标是让 20Hz 逻辑在 50ms 内留出战略 AI、数据交换和抖动余量；渲染可以独立插值，不能把逻辑帧耗时直接换算成整款游戏 FPS。
