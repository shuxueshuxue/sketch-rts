# 替换比赛后的房间重连

完整房间验收发现：服务器已经将比赛换为带研究兵营的场景，刷新客户端却长期停留在地图配置生成的初始单位和第 0 帧。真实 WebSocket 记录显示客户端依次发送加入和 `initial-sync` 快照请求；请求使用默认 epoch 0，服务器实际已因替换比赛进入 epoch 1，拒绝了旧请求。之后收到的握手只更新编号，没有再次请求快照，客户端因此无法追上服务器状态。

现在连接打开只发送加入，客户端收到属于自身房间和玩家的握手后，采用服务器 epoch 再请求初始快照。继续使用已有快照恢复、帧缓冲和 epoch 隔离；不增加 HTTP 快照初始化，不放宽旧会话消息的拒绝规则。

回归测试通过真实 `RoomNetHub` 和房间主机建立比赛、替换场景并前进 13 帧，按浏览器网络事件顺序延迟交付握手。客户端初始快照没有测试兵营，交付网络消息后完整快照必须等于服务器状态，并记录一次初始请求和恢复。该测试在旧代码下因快照不相等失败，新代码通过。另验证观察者以服务器 epoch 同步且仍无命令权限，以及其他房间或玩家的握手不会改变会话。

定向测试共 34 项通过：锁步客户端 20、服务端部署适配器 11、WebSocket 传输 3。真实浏览器复验记录了加入、epoch 1 握手、epoch 1 初始请求、包含兵营的快照和恢复事件；之后客户端在第 55 帧已有兵营，使用真实小地图和游戏画布点选后，第 69 帧焦点准确为 `ui-research-barracks`。服务端无帧应用错误、失步或校验差异。浏览器与服务器读数相隔一个事件轮次，帧号可能差一帧，不把非原子读取当作同帧比较。

完整房间浏览验收仍沿用原 5 秒等待、精确兵营 ID 与研究按钮断言。脚本读取交互坐标时明确选择 `.game-canvas`，避免误取渲染器插入的隐藏分层画布；这是实际交互元素修正，不替换选择或渲染逻辑。此次证据使用 2D 功能验收，不作 FPS 结论。
