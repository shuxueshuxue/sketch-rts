实际半径缩小 **35.7%**，实际保护面积缩小 **58.7%**。180 接近旧椭圆的等面积圆半径 `280 × √0.42 ≈ 181.46`；新外圈几何面积相对旧可见椭圆只缩小约 1.6%。这是同时缩小真实保护范围、修正被压扁的纵向边界，并非只放大特效。原描边、光晕、内部脉冲和盾形符号仍沿用现有美术语言；光晕没有额外选中含义。

Canvas 的 `worldToScreen` 只平移坐标，随后由 `drawWorld` 统一缩放。3D 的 `configureWorldCamera` 用正交视口补偿倾角，使高度 0 的地面点与 Canvas 同坐标；守护卷轴不属于 GPU `PHYSICAL_EFFECTS`，使用同一个 Canvas overlay。因此新圆同时对齐两种路径的地面坐标。三种缩放（0.6、1、1.8）、每种 16 个真实 Three 相机投影边界点已验证。卷轴事件使用 `sourceId`；与半径同为 180 的老兵守护技能使用 `unitId` 的区分保留，没有误进入老兵动画路径。

选择仍发生于施放时，包含本人、同队友军及机械友军，排除敌军、野怪和舱内单位。原有按单位中心距离判定保留，不改为身体边缘判定；模型自身的高度、脚部绘画偏移不改变命中规则。选中的单位离开原地仍保有剩余 7 秒保护；后来进入圆内的单位不会获得保护。圈记录原施放位置，受益单位各自仍显示原有守护状态。

## 已知 AI 受益人数估算差异，未应用策略修改

`src/ai/policy/item-tactics.ts` 的启用条件仍在 **260** 内找至少四名尚未受保护的本方战斗单位；同模块的本轮覆盖记录已经读取 `GUARDIAN_SCROLL.radius`。冻结 `policy-v2prod` 的对应启用条件也保持 260。现有源码没有把 260 定义为 `radius - 20`，也没有解释该固定值的原始设计意图，不能仅凭 `280 - 20 = 260` 宣称它是安全边距。

真实只读诊断固定携带者与距离 245、250、255 的三名友军，以及 300 内三名敌军。旧、新源码均给出相同 `useItem` 命令；旧半径保护四名，新半径只保护携带者。见 `visual/before-ai-diagnostic.json`、`visual/after-ai-diagnostic.json`。因此范围改变后启发式可能高估受益人数，已有 49 项集中阵列检查通过并不能否定该问题。

供用户另行决定的最小策略同步提案：将共享策略的受益筛选从固定 260 接到实际半径 180，保留至少四人、敌军接触距离和决策顺序；这会让上述分散阵列不再使用卷轴，是明确的 AI 决策变化。若产品选择保留旧数值的 20 单位内缩，则新阈值为 160，会额外排除 160～180 内真实能受益的友军；当前没有证据必须保留这层内缩。两种提案都**未应用**，整个 `src/ai` 与基线逐字节相同，冻结源码、路线、基线、验收条件和思考相位未修改。

实现和证据作为独立范围平衡提交审阅，未合并、未部署。
