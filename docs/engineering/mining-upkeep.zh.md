# 连续采矿维护费与金币结算

以一个满载金矿的毛收入 I 为基准。用户锚点要求 40、70、100、130 人口分别需要 1、2、3、4 个满载金矿才能保持基准可支配收入；因此插值的是所需矿数 N(P) = 1 + (P − 40) / 30，而非收入百分比。维护后收入比例为 r(P) = 1 / N(P) = 30 / (P − 10)。多个同等矿的总收入为 N × I × r(P) = I。55 人口对应 1.5 个矿、收入 2/3；85 人口对应 2.5 个矿、收入 2/5。

40 人口及以下 r(P)=1，不扣费也不补贴。这与上方曲线连续，40 处允许斜率转折。没有高人口税率下限或人口硬上限。容量仍须通过建筑获取；极高人口下理论收入趋近于零。

采用模拟器现有 supplyUsed：场上单位、船载人口、排队训练的人口均计入，工人也在内，不另外创建“战斗人口”状态。每次实际卸金按当时这一人口数结算。这里军队再生效率按用户明确给定的收入锚点解释为维持同一绝对补充预算，并非每个人口的收入；不同单位造价不参与税率计算。

玩家 gold 和存档/网络快照继续以金币为单位的 number 保存；每笔采矿所得用 Math.round(金额 × 100) / 100 结算至分。Math.round 在半分处取较大的分值；运算基于 JavaScript number 的实际值。收支通过整数分相加减再转回金币，避免反复叠加二进制小数误差。剧情奖励与场景初始金币也遵循分精度。训练、建造、研发、购买与维修共用支出入口，取消训练共用分精度入账，打野奖励独立全额入账，不经过维护费函数。

UI 向下显示整数金币，支付判断仍使用实际余额（49.99 显示 49，不能支付 50）。每笔独立舍入，不保存额外不足一分的累积状态：100 人口每趟 10 金结算为 3.33；130 人口为 2.50。由此产生至多半分/趟的量化误差；极高人口的一趟净额不足半分时会结算为零。这是分精度的边界，不是人口上限。

快照、JSON 存档和同步校验直接保留小数金币，无格式变更、迁移或旧规则兼容层。旧录像若依赖旧经济规则，其后续模拟结果自然可能变化。
