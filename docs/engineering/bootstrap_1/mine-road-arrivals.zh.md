# 矿点援军按道路到达时间选择

原来的矿点分队只按直线距离限制和排序：隔长树林的三名骑士可能排在同侧援军前面，近处慢兵也可能排在稍远的快兵前面。召唤物寿命原本已按道路行程检查，本次保留该规则。

`shared/route-selection.ts` 新增 `routeArrivals`，对可达候选各计算一次道路长度／自身速度对应的 tick，然后稳定排序。矿点分队复用它，将原 1300 行程门禁也改为道路行程，继续检查召唤物到达时仍存活。没有添加状态、缓存、阈值、直线替代道路结果或资源加成。运行时两个文件合计 +13/-3。

固定最终源码的 12 个文件、144 个不同关联检查通过。四个新原生 SDK 场景涵盖绕墙、快慢兵和镜像，候选三援军按时到场、零己方死亡和消费。精确父提交 `5a97b7159bd49cac1eeb93a9fbd65806d7068d2c` 四场均失败：快慢兵场景实际仅一名快兵到场，候选三名；绕墙场景双方最后均三名本侧兵到场，只确认旧版分队选错人，不能宣称本次独有的生存改善。

27 保存决策、79 条旧版指令及记忆相同；原冻结 54 源码哈希不变。此前两场正常 1v2 的十三个保存帧，父版与候选所有指令完全一致，没有触发矿点分队，不能把本批计为这些对局的强度改善。完整矩阵和 holdout 仍未完成。

到达时间是明确速度下的地形道路估算；身体避让、建筑绕行、地面减速、船只转向和加速不在该估算内。攻击／塔覆盖仍按实际攻击几何判断，道路行程不会改变射程。模拟每秒 20 tick，调用者使用同一时间模块，避免手写换算。
