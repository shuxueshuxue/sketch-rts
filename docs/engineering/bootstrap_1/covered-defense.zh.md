# bootstrap_1：按实际塔覆盖分开防守与退守位置

弱势近战防线不能靠附近有塔就去前方接战。旧逻辑将主基地视为必定有掩护，以基地附近的塔数代替交战点支援；等待射手的退守点固定在基地后 400，抵达后没有守位，普通自动索敌可以重新开始追击。

三个运行时文件：主军队规划器接收调用方必填的防守位置、塔后等待判定、等待命令三个选择器，普通版本显式沿用原来的计算；bootstrap 的三个 v9 家族使用同一覆盖与守位模块。没有可选兼容参数、旧行为兜底、额外寻路缓存或地图/对手特判。

## 几何与道路各做自己的工作

- 基地与塔后位置的可达性、距离排序使用已有 `walkingDistance` / `nearestByRoute`。拒绝不可步行到达或在建筑占地上的退守点。
- 火力覆盖仍按物理直线半径：普通防守点与塔后等待点分别计算塔的覆盖，含 80 单位驻守空间；支援强度计入塔剩余 HP。
- 近战面对强势射手时，前往塔后约塔射程三分之一的位置，抵达后发普通 `holdPosition`；威胁不再满足等待条件后交还普通主力指挥。伤兵、远程主力与其他任务的归属沿用原规则。

驻守位置在塔射程内并不保证每个射手都已进入塔射程，也不能靠一座塔击败无限敌军。本轮没有改属性、血量、资源或伤害。

候选原有永久战斗单位没有死亡，失去 11 名原有工人；#308 最终失去所有原有战斗单位和 15 名原有工人。短窗口里退守使前方矿线更快被攻破，长一点的局部窗口保住了主力与后方经济。双方均未结束比赛，这不是正式胜局，矿工提前转移仍是后续工作。

第一版要求覆盖驻守区外的所有敌方最大射程，拒绝了正常塔后位置，最终只剩 3 名主力和 7 工人，且三项既有矿区检查失败，已撤回。第二版把所有防守点都放到后方，保存主力却仍导致三项矿区检查失败，已拆成正常防守与弱势退守两种位置。

另外单塔对 14 射手、无遮蔽自然矿对 8 射手的手操式压力场景，新旧双方步兵都全灭；三塔场景两边都存活，候选步兵反而受伤更多。这些结果保留，不计作改善；不能把保存一处主力外推成所有防守都更强。

## 验证

新增正常单位的镜像场景只检查真实守位控制、塔实际命中、零士兵伤害/损失/花费；不把敌人固定攻击基地的控制场景当作胜率或伤害改善。三个 v9 家族各自完成镜像检查，共六项通过，到位后都真正持有普通 hold 命令。#308 main 的同六项守位断言全部失败；这个控制场景新旧士兵都无伤，没有伤害改善。

新增检查连同防守绕路、工作基地、矿区保护、伤兵恢复、开局阵线、清营与可调用战力检查共 175 项通过，进程实际退出 0。45 个普通 v5/v6/v7/v8/v9 规划场景 / 145 命令及完整记忆与 #308 main 相同。
