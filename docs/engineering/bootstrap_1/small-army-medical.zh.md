# 小部队医疗采购

实际 Pineshade 射手对冻结 v5+v7 的败局中，伤兵已出现，而尚无治疗生产建筑。部队一旦跌破十人，既有医疗需求会消失，因而建筑没有建成、医生也无法出现。

现在已经达到治疗兵种的现有科技人口门槛且确有重伤员时，小部队也会请求医疗生产与至少一名医生。普通健康部队的门槛、两名支持单位上限、采购优先级和共享反召唤队列保留。运行时一文件 +2/-2，无新状态、阈值或特殊地图分支。

十二个三路线／两族／镜像 SDK 场景，在平地控制购买契约，拥有六名既有士兵、正常500金和三名实际矿工，从没有医疗生产建筑开始，正常付费完成生产、恢复两名伤兵，资源结算和零损失断言保持。同一2400 tick的精确父版十场失败、两个 Ember 射手场景本来就通过；不把后者算独有改善。

初始合成场景没有完整的工人返矿脚本，发生收入归零；补齐实际脚本后，原地图的不对称道路与1800 tick观察窗仍使部分场景未通过。最终购买场景明确使用平地与2400 tick覆盖生产、行走和两次治疗，不改变运行时代码、金币、伤员或断言；实际地图证据另外保留。

同一个正常500金／3工人／1基地开局产生的6000 tick存档，用固定医疗候选和精确父策略续至10800：父版1基地、4战斗单位、307总剩余生命、累计损失22；候选2基地、14战斗单位、1289剩余生命、累计损失5。损失包含工人，候选牧师于9600前死亡，仍非无损。此后候选续至24000仍活着，两基地、28战斗单位，对手合计六基地，尚无胜负。它是相同中局的局部因果比较，不是固定候选从零的正式矩阵胜场。

已有经济、道路治疗、撤退、召唤编队、恢复预算和拥挤退路检查保持。27保存决策／79条旧指令和记忆相同，冻结54哈希保持。最终集成源码九文件136项原生检查通过，Node20子路径客户端／服务器生产构建实际exit 0。首次类型检查捕获新测试数组被推断为string[]，添加准确的TrainableUnitKind[]声明后再构建通过；这是测试声明修正，运行时两行差异保持。精确提交CI是合并前的另一个门禁。
