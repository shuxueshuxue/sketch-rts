# 首页三场演出与有限资产准备

本分支以主线 `a0524c2c9b32d4b92084d4f9478729eb562f7d29` 为基线。三场新演出的优化前检查点为 `a13878465d7de94311476c7c591b18fc3a39bcc4`；最初画面/性能采集时工作区尚未提交，记录中的 HEAD 因而仍是主线，逐文件字节与该检查点对应。最终执行源以每次采集的 source SHA 清单为准。

海战有两艘巨舰、23 名船员和16个真实炮位，依次炮击、伤亡、抢修、靠拢铺桥、接舷近战、换旗夺船。船体不做上下浮动。王城有24人、61件装饰和3座公共建筑，以90秒镜头展示市集、酒馆及街道生活。林间为18名正规军对22只野怪，含四个大型/首领外形，保留编队、箭阵、骑兵侧击和近战。

三场均使用有限演员及时间脚本，复用真实 WorldPresentation、模型、动作和特效路径。首页不执行完整对局的 AI、寻路或 stepGame，不改变正式对局、AI思考相位、船只规则或守护卷轴。守护卷轴范围平衡另见草稿 PR #374；本分支与 PR #373 的历史性能证据仍是规则2。

## 实测边界

主线与新演出内容不同，第一组主线/新场景 ABBA 是实际首页成本对照，不能据此把画面重做宣称为等值优化。此组12个15秒原生窗口、三场完整周期、全部负面样本和源哈希保留。真实浏览器初版海战在伤亡和镜头拉近处有重复700ms级绘制提交尖峰。

两轮逐帧归因在这些帧测到尸体卡片的 Canvas 像素读回占主要墙钟，例如485.9ms的 World3DLayer 绘制中读回477.1ms。纹理上传和 renderer.render 提交较短，程序数稳定；这些是CPU墙钟通过提交的观测，不是GPU执行时间。不能由全场累计耗时推断任一尖峰原因。

曾试图只给裁剪画布增加 willReadFrequently。六例真实 Chromium 对照显示裁剪RGBA相同、最终缩放/旋转结果不同；同源码控制组全部字节相同，排除了工具随机波动。该候选撤销，完整失败源码、输入、原RGBA和差图保留，未放宽零差异断言。

采用的方案仅在资源加载阶段准备海战七具已知的未来甲板尸体。准备与显示共用同一配方、原画法和密度2/4，并写入现有无损 CPU 卡片缓存；不提前生成尸体、不上传GPU或增加可见实例。六例实际 prepareRaster 缓存恢复对照，30项光栅比较、17,133,852字节全部相同，含底向行存储、原方向恢复、alpha、锚点和上下文属性。它只证明这些实际卡片的字节一致，并非整个世界的逐像素对照。

加载完成后重置首页演出钟，保留同一演员、模型及预热缓存，避免资源加载吃掉开场炮击。海战和王城的优化前后原生 ABBA 自然等待演出年龄至少7秒且已提交tick至少140，再测15秒；林间首次四窗因首帧阻塞而相位误配，只作为观察保留，另在自然年龄20秒做四窗有效对照。全部无seek或模拟时钟修改。具体起止年龄保留，软件渲染造成的相位采样抖动如实报告。

资源准备墙钟、准备后可见0～7秒的绘制提交、正式测量窗口分开记录。不能将初可见帧大尖峰叫作纯加载，不能只报告被移走成本后的窗口。内存报告使用浏览器JS heap和现有卡片缓存/纹理存储计数；heap前后变化不等于分配总量或泄漏，软件GPU资源估计不等于进程RSS。未强制GC，也没有测GPU计时器。

收益明确集中在海战已归因的尸体准备；王城和林间没有尸体预热，不据上述小幅差异宣称稳定收益。原海战演出和候选在同一环境、同一阶段下均保留两次重复。有效海战窗口仍有两帧超过50ms。原生 rAF 没有随 CPU 提交均值改善，完整周期也仍有582.2ms首次桥出现对应帧和150.8ms循环起点帧；不能把这种相关性进一步归因为某个shader或GC。

海战资源准备两个 A 为1769.7/1865.5ms，两个 B 为2016.5/2030.3ms。候选准备12个去重后的源光栅，压缩缓存304,640字节、该缓存及其scratch的owned CPU为437,760字节，预热GPU存储为0，峰值待处理RGBA为1,048,576字节；这些不是总进程内存或全体Canvas占用。完整统计另含外层Canvas backing及测量前GPU存储。准备后的初可见帧仍有大尖峰，其中林间记录13,664.6ms。现已观察到镜头拉近仍有100ms级活人卡片准备帧、初可见帧仍有大尖峰，不能宣称整个开场流畅或通用硬件FPS达标。原林间周期11.18秒rAF间隔的原因未确定；该间隔不能仅由当次绘制提交解释，也不被归因为GC。
