# 首页“海盗夺船”改成真实模拟：改动前后

改动前，这一幕是按脚本播的：跳板什么时候搭、谁什么时候倒下、什么时候换旗，全写死在固定的秒数上。比赛模拟从头到尾没有跑。

改动后，场景只定开局，其余全部交给比赛模拟，在 match thread（Web Worker）上跑。开局内容如下：

- 两艘战列舰并排靠着，海盗船已经停在模拟自己会选的接舷位置上。
- 每艘船上各站着一队水手。海盗 4 人，有些场次 5 人；水兵 4 人。
- 海盗船的舵手接到一条“接舷登船”命令。

跳板放下、海盗过船、甲板上的厮杀、伤亡、夺船和换旗，都是模拟真实算出来的。一方打光后，过 4 秒淡出，再用新的随机种子开下一场。

## 这一幕摆出来的开局（场景设定，不是改游戏规则）

水兵船靠海盗一侧的两门舷炮（starboard0 / starboard2）在开局时没有架出来，船上只剩背向海盗的两门。这一幕讲的是“水兵船被海盗贴上来时，那一侧的炮还没来得及架出”。游戏规则一个字没改：舷炮、跳板、登船的结算和正式对局完全一样。之所以这样摆，是因为两侧火炮都在的话，水兵船的舷炮会把跳板和刚上跳板的人一起扫掉，首页这一幕就成了“海盗冲不上去”。

截图环境：mac1 无头 Chromium，1440×900，生产构建（`vite build` 后以 `NODE_ENV=production` 起服务）。改动前基于 `main@06c0d9e6`。截图时 mac1 负载在 84–106 之间，页面主线程大部分时间拿不到 CPU。每次推进最多补 4 个 tick，超出的时间直接丢掉，所以浏览器里这一场是慢放的：模拟里 3.6 秒过船，截图里 16–24 秒才打到对面甲板上。负载正常时不会这样。

镜头按两艘船的真实尺寸取景：宽度取两船的横向跨度，高度取一个船身长。原来脚本里的船比真实战列舰大，沿用旧的取景系数会把船缩成右下角的一小团。

## 胜负与时长（种子 1–20，A100 上用 Node 直接跑 `stepGame`）

| | 海盗 5 人（12 场） | 海盗 4 人（8 场） |
|---|---|---|
| 跳板放好 | 3.0 秒 | 3.0 秒 |
| 第一个海盗踏上对面甲板 | 3.6 秒 | 4.3 秒 |
| 分出胜负 | 13.8 秒 | 14.2 秒 |
| 结局 | 夺船，海盗无人阵亡 | 夺船，海盗无人阵亡 |

每一场都是海盗赢，每场的过程也几乎一样。种子只决定海盗是 4 人还是 5 人，别的都不变。

水兵守在原位（`hold`），海盗从跳板上来后逐个对上，所以水兵每次只有一个人在打。我试过开局给水兵一条冲向跳板落点的 attackMove：海盗会死 1–2 个，但结局还是夺船。这条命令没有加进来；加不加由审阅的人决定。

## 模拟开销（A100 单核，用 `process.cpuUsage` 量 `stepGame` 本身）

| 场景 | 每 tick 均值 | p95 | 最坏一个 tick | 每秒 CPU（20 tick/秒） |
|---|---|---|---|---|
| 林间血战，种子 1 / 2 / 7 | 0.65 / 0.29 / 0.13 ms | 3.5 / 0.4 / 0.2 ms | 49 / 15 / 13 ms | 13 / 6 / 3 ms |
| 海盗夺船，种子 1 / 2 / 7 | 11.1 / 8.6 / 5.7 ms | 30 / 19 / 14 ms | 148 / 39 / 21 ms | 223 / 171 / 115 ms |

这一幕的模拟比林间血战贵一到两个数量级，主要花在甲板上的走位上。它跑在 worker 里，不占页面主线程，但只要首页开着就一直在耗 CPU。

mac1 上的 Chrome trace 这次不能作数。负载在 84–106 之间时，渲染主线程每秒 650–920 ms 的墙钟时间里只拿到 10–20 ms CPU，worker 大部分时间在等页面发推进请求，测出来的是机器有多饿，不是场景有多贵。
